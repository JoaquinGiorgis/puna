# ERC-8004 en Fuji — gotchas y smoke test (H0)

Fuente de direcciones: https://github.com/erc-8004/erc-8004-contracts (sección Avalanche Testnet).

## Firmas que usa PunaEscrow (`contracts/src/interfaces/IERC8004.sol`)
- `validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash)`
- `validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)`
- `getValidationStatus(bytes32) → (validatorAddress, agentId, response, responseHash, tag, lastUpdate)`
- `giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)`: confirmado en H0. El escrow igual lo llama con try/catch.

## Reglas verificadas
- Solo el dueño (u operador) del agente llama a `validationRequest`. Por eso lo llama el nodo, no el escrow.
- Solo el `validatorAddress` nombrado llama a `validationResponse`.
- `response` es 0–100 y se puede pisar. El escrow lee una sola vez en `settle`.
- `requestHash` es único global. El escrow lo deriva de `chainid`, escrow, job, intento, agente, hashes e índice.
- Reputation revierte si el dueño del agente se califica a sí mismo.
- El README oficial no lista Validation para Avalanche testnet, pero **está desplegado y funciona** (smoke test H0, 11/11).

## Verificado en Fuji (H0, 11/11/2026)
Proxies EIP-1967; ABIs verificados en Routescan, compilados con solc 0.8.24.

| Registro | Proxy | Implementación |
|---|---|---|
| Identity | `0x8004A818BFB912233c491871b3d84c89A494BD9e` | `0x7274e874ca62410a93bd8bf61c69d8045e399c02` (IdentityRegistryUpgradeable) |
| Reputation | `0x8004B663056A597Dffe9eCcC1965A193B7388713` | `0x16e0fa7f7c56b9a767e34b192b51f921be31da34` (ReputationRegistryUpgradeable) |
| Validation | `0x8004Cb1BF31DAf7788923b405b754f57acEB4272` | `0xdb31f5d9167f8ebc8b30fbbf814c4d297c2d7f99` (ValidationRegistryUpgradeable) |

Firmas confirmadas; todas coinciden con `IERC8004.sol`, sin cambios:
- `register()`, `register(string agentURI)`, `register(string agentURI, (string metadataKey, bytes metadataValue)[] metadata)` → `uint256 agentId`. Emite `Registered(uint256 indexed agentId, string agentURI, address indexed owner)`.
- `ownerOf(uint256) → address`.
- `validationRequest(address,uint256,string,bytes32)`: exige `msg.sender` dueño, `isApprovedForAll` o `getApproved`; `requestHash` no usado (`"exists"`).
- `validationResponse(bytes32,uint8,string,bytes32,string)`: exige `msg.sender == validatorAddress` (`"not validator"`) y `response <= 100` (`"resp>100"`).
- `getValidationStatus(bytes32) → (address validatorAddress, uint256 agentId, uint8 response, bytes32 responseHash, string tag, uint256 lastUpdate)`.
- `giveFeedback(uint256,int128,uint8,string,string,string,string,bytes32)`: coincide con la v1.

Smoke test: `.venv/bin/python scripts/smoke_erc8004.py`. Los hashes están en `docs/txs.md`. **Plan B no hace falta.**

## Smoke test H0 (issue #1)
1. Registrar dos agentes en Identity (nodo ORBIT-07 y ORBIT-03) y un validador.
2. `validationRequest` desde el dueño del agente, con un `requestHash` cualquiera.
3. `validationResponse` desde el validador.
4. `getValidationStatus` devuelve lo esperado.
5. Guardar los hashes de tx en `docs/txs.md`.

**Plan B** si falla el paso 2 o el 3: el escrow verifica una firma EIP-712 del validador con `ecrecover` sobre `(requestHash, score, responseHash)`, y ERC-8004 queda solo para Identity y Reputation.
